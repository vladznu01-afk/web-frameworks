Теоретичні відомості 
У роботі поєднано чотири механізми: спостереження за реактивними

коли нижній маркер каталогу наблизився до видимої області. 
1. Спостерігачі у Vue 
Реактивне значення саме по собі лише зберігає стан. Щоб у відповідь на 
його зміну виконати дію — скасувати запит, запустити таймер або отримати нову 
сторінку — використовують спостерігач. 
Vue має два основні засоби спостереження: watch() і watchEffect(). 
watch: джерело задається явно 
watch() відокремлює джерело від побічного ефекту. Він викликає 
callback, коли значення джерела змінилося, і передає нове та попереднє значення. 
 
const query = ref('') 
  
watch(query, (nextQuery, previousQuery) => { 
  console.log({ nextQuery, previousQuery }) 
}) 
 
Джерелом може бути ref, гетер, реактивний об’єкт або масив джерел. Для 
властивості реактивного об’єкта передають гетер, а не поточне значення: 
 
watch(() => filters.category, (category) => { 
  // category — нове значення filters.category 
}) 
 
У цій роботі watch() доречний там, де залежність має бути очевидною: 
- сирий query змінився — активний HTTP-запит більше не відповідає 
наміру користувача, тому його потрібно скасувати;

- змінився пошуковий рядок після debounce — потрібно скинути skip і 
накопичені товари; 
- надійшла нова сторінка API — її потрібно замінити або додати до 
каталогу. 
Для негайного скасування запиту використовується { flush: 'sync' } . 
Синхронний callback виконується під час зміни значення, до звичайної черги 
оновлень Vue. Такий режим придатний для короткої операції abort(), але не для 
важких обчислень або спостереження за масивом із багатьма синхронними 
змінами. 
watchEffect: залежності визначаються під час виконання 
watchEffect() запускає callback одразу й автоматично запам’ятовує всі 
реактивні значення, прочитані під час його синхронного виконання. 
 
watchEffect(() => { 
  document.title = 'Знайдено: ' + total.value 
}) 
 
Після зміни total.value ефект виконається знову. На відміну від 
watch(), окремий список джерел тут не задається. 
Для асинхронного callback діє важливе обмеження: Vue відстежує лише 
значення, прочитані до першого await. Тому URL запиту потрібно отримати на 
початку ефекту: 
 
watchEffect(async (onCleanup) => { 
  const currentUrl = toValue(url) 
  const controller = new AbortController() 
  
  onCleanup(() => controller.abort()) 
  
  const response = await fetch(currentUrl, { 
    signal: controller.signal, 
  }) 
}) 
 
Якщо викликати toValue(url) лише після await, зміни реактивного URL 
не стануть залежністю цього ефекту. 
Очищення попереднього запуску 
Перед повторним запуском спостерігача Vue викликає зареєстровану 
функцію очищення. Вона має звільнити ресурс, створений саме цим запуском: 
- clearTimeout() видаляє попередній debounce-таймер; 
- AbortController.abort() скасовує застарілий запит; 
- функція відписки припиняє слухання події або іншого джерела. 
Це захищає від змагання запитів. Без скасування повільна відповідь для 
старого рядка може надійти після нової та перезаписати актуальні дані.

Скасований запит є очікуваним завершенням роботи, тому він не повинен 
відображатися як помилка інтерфейсу. 
Debounce і скасування не замінюють одне одного. Debounce відкладає 
створення наступного запиту, а abort() припиняє запит, який уже виконується. 
У лабораторній сирий query керує негайним скасуванням, а відкладений 
debouncedQuery — формуванням нового URL. 
2. Composable як власник реактивної логіки 
За визначенням Vue, composable — це функція, яка використовує 
Composition API для інкапсуляції та повторного використання логіки зі станом. 
Назва такої функції за домовленістю починається з use. 
Звичайна функція перетворення отримує аргумент і одразу повертає 
результат. Composable може зберігати реактивний стан, створювати спостерігачі, 
реєструвати lifecycle hooks і змінювати результат із часом. 
 
export function useRequestState() { 
  const data = ref(null) 
  const error = ref(null) 
  const isLoading = ref(false) 
  
  return { data, error, isLoading } 
} 
 
Рекомендований контракт повернення — звичайний об’єкт, властивостями 
якого є ref. Його можна деструктурувати без втрати реактивності: 
 
const { data, error, isLoading } = useFetch(url) 
 
Кожен виклик composable створює окремий стан, якщо цей стан оголошено 
всередині функції. Два компоненти, які викликали useFetch(), не повинні 
випадково використовувати один isLoading або один AbortController. 
Межа відповідальності 
Composable інкапсулює механізм, але не розмітку. Наприклад, useFetch 
знає, як виконати й скасувати запит, однак не вирішує, як виглядає картка товару. 
Компонент показує дані та передає події, але не повинен відтворювати власну 
реалізацію мережевого запиту або observer. 
У цій роботі межі мають такий зміст: 
Модуль Ресурс або стан, яким він володіє 
useFetch HTTP-запит, AbortController, data, 
error, isLoading 
useDebouncedValue таймер і відкладене реактивне значення 
useIntersectionObserver екземпляр IntersectionObserver і 
підписка на ціль 
компонент розмітка, пропси, події та локальний 
стан представлення

Модуль, який створив ресурс, відповідає і за його очищення. Компонент 
не має знати ідентифікатор таймера з useDebouncedValue, а App.vue не повинен 
викликати disconnect() для observer, створеного всередині composable. 
Composable викликають синхронно у <script setup> або setup(). Тоді 
Vue може прив’язати його спостерігачі та lifecycle hooks до поточного 
екземпляра компонента й зупинити їх під час розмонтування. 
3. Передавання параметрів і toValue() 
Найпростіший composable приймає звичайне значення. Для повторно 
використовуваної реактивної логіки цього часто недостатньо: споживач може 
мати готовий ref або потребувати обчислювати параметр із кількох станів. 
Vue використовує тип MaybeRefOrGetter<T> для трьох припустимих 
форм входу: 
Форма Приклад Поведінка 
звичайне значення useFetch('/api/products') значення не змінюється 
реактивно 
ref useFetch(url) зміна url.value 
повторює ефект 
гетер useFetch(() => 
'/api/products?q=' + 
query.value) 
ефект залежить від 
значень, прочитаних 
гетером 
 
Гетер особливо корисний для пропсів і похідних параметрів. Передавання 
props.id копіює його поточне значення, тоді як () => props.id  зберігає 
реактивний зв’язок із пропсом. 
Нормалізація входу 
toValue() повертає однаковий результат незалежно від форми аргументу: 
 
toValue('/api/products') 
toValue(ref('/api/products')) 
toValue(() => '/api/products') 
 
У всіх трьох випадках результатом буде рядок '/api/products'. Для ref 
функція читає .value, для гетера — викликає його, а звичайне значення повертає 
без змін. 
unref() також розкриває ref, але не викликає гетер. Якщо передати до 
unref() функцію, результатом буде сама функція. Саме тому для параметра 
типу MaybeRefOrGetter<T> використовують toValue(). 
Місце виклику визначає реактивність 
Нормалізація має відбутися всередині реактивного ефекту:

export function useFetch(url) { 
  watchEffect(async (onCleanup) => { 
    const currentUrl = toValue(url) 
    // currentUrl використовується для поточного запуску 
  }) 
} 
 
Якщо виконати toValue(url) один раз до watchEffect(), composable 
отримає лише початковий рядок. Спостерігач не побачить читання url.value 
або реактивних залежностей гетера, тому не зможе повторити запит після їхньої 
зміни. 
Гнучкий вхід не означає, що composable має змінювати аргумент. Вхід 
читається через toValue(), а власний стан повертається окремими ref. Якщо 
споживач не повинен змінювати результат напряму, його повертають через 
readonly(). 
4. IntersectionObserver 
IntersectionObserver — браузерний API для асинхронного 
спостереження за перетином елемента з видимою областю або заданим 
контейнером. Для нескінченного прокручування цільовим елементом стає 
невеликий маркер після списку товарів. 
Observer працює з такими поняттями: 
- target — DOM-елемент, за яким спостерігають; 
- root — контейнер спостереження; значення null означає viewport; 
- rootMargin — відступ навколо меж root, записаний за правилами CSS 
margin; 
- threshold — частка видимої площі цілі, після перетину якої 
викликається callback; 
- IntersectionObserverEntry — запис зі станом перетину, зокрема 
isIntersecting та intersectionRatio. 
 
const observer = new IntersectionObserver( 
  (entries) => { 
    for (const entry of entries) { 
      if (entry.isIntersecting) { 
        loadMore() 
      } 
    } 
  }, 
  { 
    root: null, 
    rootMargin: '280px 0px', 
    threshold: 0.01, 
  }, 
) 
 
Додатний вертикальний rootMargin розширює область спостереження. 
Маркер вважається близьким до viewport ще до того, як користувач побачить

6 
кінець каталогу. Значення threshold: 0.01 означає, що callback спрацює після 
появи приблизно одного відсотка цілі в розширеній області. 
На відміну від обробника scroll, observer не вимагає на кожній події 
вимірювати позиції елементів через getBoundingClientRect(). Браузер сам 
відстежує перетин і передає зміни callback. Водночас observer лише повідомляє 
про подію: він не знає, чи можна зараз завантажувати сторінку. 
Перед зміною skip застосунок має перевірити: 
- попередній запит завершився; 
- помилки немає; 
- debounce не очікує нового пошукового рядка; 
- кількість отриманих товарів менша за total. 
Один маркер може залишатися в області перетину під час кількох оновлень 
DOM, тому без цих умов легко надіслати повторні запити з однаковим skip. 
Життєвий цикл observer 
DOM-елемент шаблонного ref відсутній до монтування компонента. Тому 
IntersectionObserver створюють у onMounted(), після появи цілі викликають 
observe(target), а під час зміни цілі припиняють спостереження за попереднім 
елементом. 
Під час розмонтування потрібно викликати disconnect(). Це від’єднує всі 
цілі та не дозволяє callback звертатися до стану компонента, якого вже немає. 
Перевірка наявності window та IntersectionObserver захищає код у 
середовищі без DOM, зокрема під час серверного рендерингу. 
У підсумку потік нескінченного прокручування має такий вигляд: 
 
маркер наблизився до viewport 
  → IntersectionObserver повідомив про перетин 
  → компонент перевірив умови завантаження 
  → skip збільшився 
  → реактивний URL змінився 
  → useFetch отримав наступну сторінку 
  → нові товари додано без повторення id

- CatalogLoadMore показує стан наступної сторінки, спостерігає власний

3. Перенесення розмітки до компонентів 
Спочатку розподіліть готову розмітку без зміни поведінки. Після кожного 
перенесення перевіряйте сторінку у браузері, щоб знайти втрачений клас або 
пропс у межах одного кроку. 
ProductCard отримує обов’язковий пропс product. Перенесіть до нього 
розмітку article.product-card і форматування ціни. Компонент не читає API, 
не знає позицію картки в масиві й не змінює товар. 
ProductCatalog отримує пропси products, isLoading та error. Він 
відтворює ProductCard через v-for, використовує product.id як key і показує 
готові стани початкового завантаження, помилки та порожнього результату. 
Повторний запит передайте подією retry. 
ProductSearchForm реалізує контракт v-model. Оголосіть пропс 
modelValue типу String і подію update:modelValue. Поле передає введений 
рядок назовні, але компонент не створює fetch, URL або таймер. 
CatalogLoadMore отримує loaded, total, isLoading, error і hasMore. 
Він показує готовий нижній блок і надсилає події load-more та retry.

4. Composable для HTTP-запиту 
Перенесіть fetch і пов’язані стани зі стартера до useFetch.js. Функція 
приймає URL у формі звичайного значення, ref або гетера. Усередині 
watchEffect() прочитайте його через toValue() до першого await. 
Кожен запуск ефекту створює власний AbortController. Передайте його 
signal до fetch і зареєструйте controller.abort() через onCleanup. Під час 
нового запуску попередній контролер також потрібно скасувати. 
Composable повертає такий публічний контракт: 
 
return { data, error, isLoading, abort, refetch } 
 
Метод abort() скасовує активний запит і завершує стан завантаження. 
Метод refetch() змінює внутрішній реактивний лічильник, прочитаний 
ефектом, тому повторює запит без зміни URL. 
У catch не записуйте помилку після скасування сигналу. У finally 
змінюйте isLoading лише тоді, коли завершився поточний контролер. Старий 
запуск не повинен вимкнути індикатор нового запиту. 
Підключіть useFetch у App.vue до початкового URL і переконайтеся, що 
завантаження, помилка та повтор запиту працюють після видалення початкового 
fetch із компонента. 
5. Реактивний URL і debounce 
Змініть createInitialProductsUrl() у src/api/products.js на 
createProductsUrl(query, skip = 0) . Побудуйте параметри через 
URLSearchParams. Кожен URL містить limit=12, поточний skip і delay=1500. 
Для непорожнього рядка використовуйте шлях /products/search і параметр q; 
для порожнього — /products без q. 
Створіть useDebouncedValue(source, delay = 400) . Початкове 
значення одержіть через toValue(source). Спостерігайте за нормалізованим 
джерелом, створюйте таймер для нового значення й видаляйте його через 
функцію очищення спостерігача. Поверніть readonly-посилання, щоб споживач 
не міг обійти затримку прямим присвоєнням. 
У App.vue поєднайте сирий і відкладений стани: 
 
const query = ref('') 
const debouncedQuery = useDebouncedValue(query, 400) 
const requestUrl = computed(() => 
  createProductsUrl(debouncedQuery.value, skip.value), 
)

Передайте query у ProductSearchForm через v-model. Реактивний URL

Додайте окремий watch() для сирого query, який викликає abort() із

У Network уведіть phone кількома короткими порціями. Активний запит 
має отримати стан canceled, а запит з остаточним q=phone має початися після 
паузи. Скасування не повинно відкривати блок помилки. 
6. Накопичення сторінок 
Створіть в App.vue реактивні значення skip, products і total. 
Спостерігайте за data, яку повертає useFetch. Відповідь із skip=0 замінює 
список. Для наступної сторінки додайте лише товари, id яких ще немає в 
products. 
Обчисліть hasMore як порівняння кількості завантажених товарів із total. 
Функція loadMore() збільшує skip на 12 лише за таких умов: 
- ще існують результати; 
- запит не виконується; 
- debounce не очікує нового рядка; 
- помилки немає. 
Після зміни debouncedQuery синхронно поверніть skip, products і total 
до початкового стану. Новий пошук не повинен додавати свої результати до 
попередньої видачі. 
7. Composable для нижнього маркера 
Створіть useIntersectionObserver(target, callback, options = 
{}). Браузерний IntersectionObserver ініціалізуйте в onMounted(). Якщо API 
відсутній у window, завершіть монтування без помилки. 
Після появи DOM -елемента викликайте observer.observe(element). 
Після зміни цільового елемента припиняйте спостереження за попереднім. Для 
записів із entry.isIntersecting === true викликайте переданий callback. Під 
час розмонтування зупиніть внутрішній watch і викличте 
observer.disconnect(). 
У CatalogLoadMore створіть шаблонне посилання на кореневий маркер і 
передайте його до composable. Callback надсилає подію load-more. У App.vue 
обробіть її функцією з попереднього етапу. 
Для observer використайте такі параметри: 
 
{ 
  rootMargin: '280px 0px', 
  threshold: 0.01, 
}

8. Перевірка результату 
Відкрийте DevTools, увімкніть збереження журналу Network і послідовно 
виконайте перевірки: 
1. Початковий URL містить limit=12, skip=0 і delay=1500; після 
відповіді видно 12 карток. 
2. Швидке введення p, ph, phone скасовує активний запит; після 400 мс 
виконується один актуальний запит із q=phone. 
3. Пошук рядка, якого немає в назвах, показує порожній стан без помилки 
в консолі. 
4. Очищення поля повертає початковий каталог і запит без параметра q. 
5. Прокручування додає сторінки з skip=12 і skip=24; попередні картки 
не зникають, а id не повторюються. 
6. Новий пошук після дозавантаження починається з skip=0 і не залишає 
товари попередньої видачі. 
7. Після отримання всіх знайдених товарів нижній блок повідомляє про 
завершення й не надсилає нових запитів. 
8. Режим Offline показує помилку; після відновлення мережі кнопка 
повтору завантажує ту саму сторінку. 
9. За ширин 390 і 1440 пікселів сторінка не має горизонтальної 
прокрутки, обрізаного тексту або недоступних кнопок. 
Занесіть до таблиці очікуваний результат, фактичний URL, кількість 
карток і стан інтерфейсу. Збережіть знімки початкового каталогу, пошуку, 
дозавантаження та Network із canceled-запитом.
